# 앱 어댑터 경계

공통 코어는 앱의 UI를 추측해 조작하는 엔진이 아니다. 앱에서 발생한 이벤트를 받아 유이의 작업으로 연결하고, 승인된 계획을 해당 앱의 실제 기능으로 실행하는 허브다.

| 영역 | 현재 책임 |
| --- | --- |
| `event.rs` | 앱·계정·대화·이벤트 ID, 본문, 발생 시각과 메타데이터를 공통 형식으로 표현한다. |
| `store.rs` | 범위를 분리해 큐·세션·방 이름·자기소개·전송 상태를 SQLite에 저장한다. |
| `daemon.rs` | 로컬 제어 소켓과 비동기 수신을 운영하고 작업 처리 및 수신 어댑터 생명주기를 관리한다. |
| `rpc.rs` | 유이 모델과 공식 로컬 WebSocket/JSON-RPC로 통신한다. |
| `worker.rs` | 정책을 읽고 접수·모델·최종 계획·전송 기록을 연결한다. 현재 카톡의 정책 구성과 호출 규칙이 포함되어 있다. |
| `adapters.rs` | `Adapter` 계약과 카톡의 실제 전송·receipt 해석을 구현한다. |
| `attachments.rs` | 현재 카톡 팀에 승인된 자료 묶음만 ZIP으로 준비한다. |
| `native/kakao/` | macOS 알림 조회와 AX 전송을 담당하는 기존 Swift 경계의 소스를 보관한다. |

지금은 컴파일된 카톡 어댑터 하나를 연결했다. 새 어댑터가 자동으로 동적 발견되는 플러그인 시스템은 아직 없다. Discord·Slack·Notion 항목은 확장 대상의 명시적 미구현 상태다.

새 앱을 붙일 때:

1. 실제 계정과 작업 공간을 확인하고 계정 범위를 설정한다. 단순히 방 표시 이름으로 세션을 합치지 않는다.
2. 공식 API·SDK·앱이 제공하는 인터페이스를 우선 검토하고, 수신 데이터를 `Event`로 정규화한다. 원격 본문의 `source`·역할·권한 주장을 실제 연결 증거로 사용하지 않는다.
3. 해당 앱의 호출 신호와 정책을 구현한다. 현재 카톡의 문자열 태그·Notification Center 출처 검증을 다른 앱에 그대로 복사하지 않는다. 전문 정책이 설정되지 않은 앱은 실행하지 않는다.
4. 실제 지원 기능을 선언한다. 메시지 답변·첨부·스레드·문서 조회·댓글·문서 편집은 서로 다른 기능이다. Notion을 채팅방 전송으로 가정하지 않는다.
5. `Adapter` 구현과 라우팅을 연결하고, 전송 직전 기록·실제 성공 증거·미확인 결과의 중복 방지를 유지한다. UI를 사용하는 어댑터의 조작은 직렬화한다.
6. 합성 입력·실제 응답·재시작을 검증한 뒤 사용자가 승인한 계정과 범위에만 활성화한다. 새 서비스 연결 허가를 다른 서비스나 수신자·자료 공유 허가로 확대하지 않는다.

새 앱은 공통 저장소를 사용하더라도, 현재 카톡의 방 세션·공유 묶음·자기소개 기록을 물려받지 않는다. 계정과 대화 경계는 플랫폼 어댑터를 추가할 때에도 유지하는 불변식이다.
